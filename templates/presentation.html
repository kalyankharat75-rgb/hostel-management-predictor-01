1. Problem Statement & Proposed Solution

Why traditional hostel maintenance fails and how predictive analytics resolves it

❌ Traditional Maintenance Issues

  • Paper registers & WhatsApp logs: Inefficient tracking, lost complaints, no accountability.
  • Duplicate Ticket Clutter: 5 roommates independently report the same broken fan, spamming the queue.
  • Sunk Cost on Broken Assets: Repairing a burnt motor 4 times instead of replacing it costs more than buying a new one.
  • Purely Reactive Operations: Wardens wait for complete breakdowns before taking action.

✅ Predictive System Solution

  • Anti-Duplicate Alert Engine: Real-time 7-day window search prevents redundant tickets.
  • Dynamic Impact Prioritization: Multiplies affected user count by hazard severity weight.
  • 3-Month Moving Average (SMA) Forecasting: Forecasts upcoming failure surge per room.
  • Automated Replacement Flagging: Units with ≥ 3 complaints in 6 months are flagged for replacement.

3. Mathematical Modeling & Algorithmic Logic

Key formulas implemented in the codebase to show examiners

A. Urgency & Impact Score Formula (Feature 8)

Impact Score = Affected Students Count × Severity Weight (W)

Where severity weight depends on asset type risk:
• Electrical (Fan, Light, Switchboard): $W = 3$ (Sparks, heat hazard, total darkness)
• Plumbing (Geyser, Tap): $W = 2$ (Water leakage, hygiene disruption)
• Other Assets: $W = 1$

B. 3-Month Simple Moving Average (SMA) Trend Prediction (Feature 4)

SMA_{3} = (C_{month-1} + C_{month-2} + C_{month-3}) / 3

If acceleration slope $S = C_{month-1} - C_{month-2} > 0$ and $C_{month-2} > C_{month-3}$, the system flags an Accelerating Wear Surge and projects next month estimate:
Projected Low = C_{month-1} + 1, Projected High = C_{month-1} + S + 1.
(E.g., Room 204: 2 → 3 → 5 trend yields projected 6 – 8 complaints next month!)

C. Asset Replacement Policy Threshold (Feature 3)

Flag "Needs Replacement" IF Recent Complaints (T ≥ Now - 180 Days) ≥ 3

Prevents diminishing returns on maintenance labor. Instead of repeating repairs on exhausted assemblies, the system highlights candidate appliances directly to the hostel procurement office.

4. Relational Database Schema (SQLite)

Normalized database entities and foreign key associations

👤 Users Table

• id: INTEGER PRIMARY KEY
• name: TEXT
• email: TEXT UNIQUE
• password: TEXT
• role: TEXT ('student' | 'admin')
• room_no: TEXT
• floor: INTEGER

⚙️ Assets Table

• id: INTEGER PRIMARY KEY
• room_no: TEXT
• floor: INTEGER
• asset_type: TEXT
• asset_code: TEXT ('Fan-1', etc.)

📋 Complaints Table

• id: INTEGER PRIMARY KEY
• user_id: INTEGER FK (nullable if anon)
• asset_id: INTEGER FK
• room_no: TEXT, floor: INTEGER
• issue_type, description: TEXT
• date_filed, status: TEXT
• is_anonymous: INTEGER (0/1)
• affected_students_count: INTEGER

📝 Resolution_Log Table

• id: INTEGER PRIMARY KEY
• complaint_id: INTEGER FK
• resolved_date: TEXT
• resolved_by: TEXT
• remarks: TEXT (Action taken)
